# KICKOFF — Key Personnel: what constrains filling and keeping an opening at a small technical firm whose hires must satisfy a contract or a customer

You are building **Key Personnel**, a static web app that is an evidence-graded guide for a recruiter or hiring lead at a small technical firm whose hires must satisfy a labor category, a key-personnel clause, a rate ceiling, a clearance or a customer's approval. You are the build-and-delivery role; the content has already been researched and sits in `content-pack/`. **The wordmark is "Key Personnel"** (not "Key Personnel Explorer").

**Content mode: `topic`.** Read `content-pack/manifest.yaml` first and confirm it matches. The reader's body is `review.md`, a **commissioned guide written by the builder** from a scoped sweep of published studies and public government sources. `content-pack/scope.yaml` holds the scoping interview, the search strategy (500 queries with hit counts) and the corpus profile, and it is *published content*, not metadata: `/methods` renders it. The guide's promise is traceability, so the citation rules in §1 are hard build gates, not warnings.

**This pack carries extension files** beyond the standard topic-mode set: `stages.yaml`, `patterns.yaml`, `constraints.yaml`, `levers.yaml`, `gates.yaml`, `enablers.yaml`, `indicators.yaml`, `links.yaml`, `states.yaml`, `controversies.yaml`, `changes.yaml`, `hypotheses.yaml`, `queries.yaml`, `pathfinder.yaml`. ## 1. Hard rules

- **Never invent content.** Definitions, summaries, explanations, figures, effect sizes, thresholds, dates, dollar amounts, statute names — all come from `content-pack/`. If something is missing, render an amber `TODO(author)` marker (`.bx-todo`) and list it on `/methods`. Do not fill gaps from your own knowledge. Employment law, clearance rules and contract rules change often and you do not know the current ones.
- **Body text is rendered as written.** Structure it, link it — never rewrite or paraphrase `review.md`, a record's `what`, `mechanism`, `how_to_tell`, `what_it_does_not_do`, an edge's `evidence`, a ledger entry's `evidence`, or any other pack prose.
- **Uncited prose fails the build.** Any block of ≥ 25 words in `review.md`, in a concept body, in a glossary `definition` or in an extension-record prose field with no `[n]` and no `<!-- framing -->` marker (immediately before it, or inside the block) is a content-build error (APP-SPEC §6.1). List it in `BUILD-ERRORS.md` and surface it on `/methods`. **Do not fix it by adding a citation.** Record prose in the extension files is cited the same way and counts as citing text for the "reference never cited" check: a reference cited only from a record is cited.
- **`<!-- synthesis -->` blocks stay visible**, and so does the records' own marker: any record field whose text contains the literal `(synthesis)` renders with the same quiet left rule and "synthesis" label as a review block, gets an id, and is linked from `/methods`. Never strip either marker.
- **Nothing implies peer review, official status, or advice.** `manifest.venue` and `manifest.disclaimer` say what this is; render the disclaimer in the footer of every page and in full on `/about`. `as_of` appears on `/`, `/read` and `/about`, and every record page shows its own `as_of`. No page uses the second person imperative to tell a reader what to do about their opening ("the rule requires…" and "the study found…" are fine; "you should…" is not); if pack text does, it is a pack error — record it, do not render it changed. **Nothing is ever recommended**: the pathfinder ranks by match count and says so; levers are listed with their evidence grade and never ordered by any merit score.
- **No firm.** There is no account, no server-side state, no analytics beacon, and no firm named anywhere in the UI. Personalisation (the pathfinder answers, the decision record, the notepad, saved filters) lives in `localStorage` only, with a visible "stays in this browser" note. The one thing that leaves the browser is stated where it happens: `/benchmarks` shows figures that a scheduled workflow refreshed from the BLS public API at build time (§4c); no page fetches at runtime.
- **Effect sizes render exactly as the record carries them**, with the population beside them. A lever page always shows `evidence.grade`, `evidence.effect`, `evidence.population` and `evidence.k_n` together, and `what_it_does_not_do` directly beneath, in that order; a lever may not be shown without its limits line.
- **The ledger is a ledger.** `hypotheses.yaml` holds the author's original guesses, each with a status. A hypothesis is never rendered as a fact or as a record; it appears only on `/methods` (the full ledger) and, where a record carries `legacy: [h-…]`, as a small "tested the author's guess h-A3: supported" line linking into the ledger. The matrix the ledger came from is not in the pack and must not be referred to as a source.
- **Compilation-sourced is shown as such.** Every `states.yaml` overlay carries `primary_pending`; when it is `true` the overlay renders with a visible "compilation-sourced; statute not yet read" tag, and a state page says in its header how many of its nine overlays carry the tag. A status of `none-found`, `not-checked`, `reported` or `unresolved` renders with the file header's meaning of that word, never as "no law".
- **Pending is pending; superseded is struck.** `pending_changes[]` renders as a labelled block on each record with its status word and date. A `changes.yaml` entry whose `what` begins with `Superseded:` (ch-006) renders struck through with the superseding entry linked, and is never shown as current.
- **Where sources disagree, show both.** A record's `conflicts` list renders visibly as "Where sources differ"; a reference's `recheck: true` renders on its card as "not yet re-read against the live page" (every reference carries it at this build — say so once on `/methods` rather than hiding it).
- **No runtime fetches of pack content.** Everything in `content-pack/` ships in `dist/`.
- **Fail loudly in the content build.** Schema violation, unresolved `[n]`, unknown term/concept/figure/record id, a link endpoint that is not a record, a `situations` tag outside the pathfinder vocabulary, a `legacy` id not in the ledger, a `mapped_to` id not a record, a state overlay missing a field, missing data file, ambiguous term variant → non-zero exit with a clear list. Do not "fix" the pack silently; write `content-pack/BUILD-ERRORS.md` and continue building the app with whatever validated (the errors also surface on `/methods`).
- **Delivery mode is `pages`** and it is not yours to change. The app ends up public — see §6b.
- **GitHub identity:** `danieladamek`. Verify with `gh auth status` before any push. **The repo does not exist yet**: create it in §6b.

- **Record pages everywhere** render `conflicts` as "Where sources differ", `pending_changes` as a labelled block, `(synthesis)` marks as synthesis blocks, and the legacy line as a link into the ledger; nothing in a record is reordered or reworded.

### What these surfaces must not do

- No constraint, lever or enabler is ever recommended, scored beyond the match count, or ranked by anything but the pathfinder rule and the user's filters.
- No text tells a reader what to do about their opening; records state what rules require, what studies found and what a lever has not been shown to do.
- No firm-specific content, example firm, or invented example anywhere in the UI; the hypothesis ledger's `original` text is the author's generalised wording and is shown only on `/methods` and in legacy lines.
- No runtime network call from any page.

## 4c. The benchmark refresh and the workflows

- **`scripts/refresh-bls.mjs`:** for every indicator with a non-empty `series`, request the latest value from the BLS Public Data API v1 (the no-key GET endpoint under `api.bls.gov/publicAPI/v1/timeseries/data/`; confirm the exact path and the response shape from the BLS API documentation page before writing the script, and record the path in the README), and write `public/data/benchmarks/latest.json` (`fetchedAt`, per series: `series`, `period`, `value`, `status`, `error?`). The four series carried at this build are `JTS540099000000000JOR`, `JTS000000000000000QUR`, `CIU2020000000000A` and `CMU2030000000000P`; the last is not confirmed as published by BLS, so a failed request for it is reported, not retried. The app shows the refreshed value **beside** the pack's value with its period, labelled "BLS, refreshed <date>", and never overwrites the pack's figure or its citation; if the data file is missing (a local build), the page shows the pack values alone and says so. Exit non-zero on a failed request **but** leave the other series' output in place.
- **`.github/workflows/deploy.yml`:** `npm ci → npm test → npm run build:content → npm run refresh:bls → npm run build` (with `BASE_PATH=/key-personnel/`) → copy `dist/index.html` → `dist/404.html` → `actions/upload-pages-artifact` → `actions/deploy-pages`. Triggers: push to `main`, `workflow_dispatch`, and `schedule: cron "23 10 * * 1"` (weekly; the schedule run only re-refreshes and redeploys). The refresh output is **never committed**; `public/data/benchmarks/` is in `.gitignore`. Use the current major versions of `actions/checkout`, `actions/setup-node`, `actions/upload-pages-artifact`, `actions/configure-pages` and `actions/deploy-pages` that run on Node 24.
- **`.github/workflows/probe-sources.yml` and `scripts/probe-sources.mjs`:** a weekly probe that requests the BLS endpoint for each series and each reference URL marked `recheck: true` with a HEAD or ranged GET, exits non-zero on any non-2xx/206 status so a blocked source shows red, and writes a Markdown summary. Do not fetch bodies; do not run it at build time.
- **Local builds** (`npm run build` on Daniel's machine) must not require the refresh: `npm run refresh:bls` is a separate script, and `/benchmarks` degrades as described above when the data file is absent.
